# M0 — Research & design

> Date: 2026-11-23 · Branch: `m0-research` · No application code in this milestone.

## Like I'm 10

Shops and freelancers in Germany now get some bills as computer files (XML) instead of normal pages. People can't
read these files without special software. Most of their other bills are still PDFs and photos. Before building an
app that sorts and checks all of these bills, we first looked up the real rules in the official law books and
government pages. Then we tried the official "bill checker" program ourselves to see that it really works. We also
drew a map of the whole app: which part does what, where the AI helps, and where it is not allowed to help. Last, we
wrote down questions to ask real people, so we build something they actually need.

## Technical

**Research** ([docs/research/einvoicing.md](../research/einvoicing.md)):
- 49 facts, each with an ID (F1–F49), an official source and a status: confirmed, caveat or unverified.
- Sources: the VAT Act and its ordinance (gesetze-im-internet.de), the BMF FAQ (as of 29 Oct 2026), KoSIT
  (XRechnung, validator, test suite), FeRD/FNFE (ZUGFeRD/Factur-X), the European Commission (EN 16931), DATEV and
  Microsoft Learn.
- Key findings that shape the design:
  - The XML is the legally leading part of hybrid invoices (F15).
  - Validation is not a legal prerequisite for input VAT (F16), so findings are "please check" hints.
  - ZUGFeRD MINIMUM/BASIC-WL are not e-invoices (F3).
  - A free ELSTER viewer exists and DATEV Unternehmen online handles e-invoices (F17, F49), so viewing alone is not
    a product.
  - Many documents stay non-e-invoices for good (F11–F13).

**Validator smoke test** ([evidence log](../research/evidence/validator-smoke-2026-11-23.txt)):
- Ran the official KoSIT validator v1.6.3 with the XRechnung configuration 2026-08-31 on official test-suite files,
  in a Java 21 container. All downloads were checked with SHA-256.
- CLI: 3 acceptable, 1 rejected (exit code 1). Our deliberately broken total produced BR-CO-15/BR-CO-16 errors.
- Daemon: HTTP 200 (acceptable), 406 (rejected), 422 (not XML), 405 (GET with GUI off); health `UP`.
- It also showed:
  - plain EN 16931 invoices are covered by the official configuration
  - warnings don't reject
  - the JVM heap must be capped in containers

## For interviews

**Say it in 6 sentences:**
1. "Before writing any code I verified the German e-invoicing rules against primary sources: the VAT Act, the
   Finance Ministry's FAQ, and the official KoSIT and FeRD standards. I recorded every fact with its source and a
   confidence status."
2. "That research changed the design. The XML is legally leading in hybrid invoices, and validation is only
   advisory. So the app reads XML deterministically, shows findings as hints rather than verdicts, and checks
   whether the PDF and the XML agree."
3. "I used an LLM only where no structured data exists, like plain PDFs and photos. Its output is never trusted
   directly: code verifies every field (maths, formats, whether the value appears in the document) and routes
   uncertain fields to a human."
4. "The official validator is a Java tool. Instead of re-implementing the rules, I run it in daemon mode as an
   internal-only container and call it over HTTP from Python. I tested that end to end before committing to it:
   200 for valid, 406 for rejected invoices."
5. "I planned Azure Container Apps first because it scales to zero and gets real users early. AKS comes later as a
   time-boxed migration with a cost cap, so I can compare both on a running system."
6. "Licences mattered too. Official XRechnung test data is Apache-2.0, but the ZUGFeRD sample invoices have no
   redistribution licence. So the test-data pipeline fetches pinned, checksummed releases and never commits
   unlicensed files."

**Likely questions and good answers:**

- **Why not let the LLM read everything, including XML?** XML is exact, free to parse and legally leading. An LLM
  would add cost, non-determinism and a chance to contradict the legal source. The LLM is for documents that have no
  structure.
- **How do you know the LLM extraction is right?** Self-reported model confidence isn't reliable. We derive
  confidence from checks in code: IBAN checksum, VAT-ID format, net + VAT = gross per rate, and whether the value
  appears in the PDF text. Fields that fail go to human review, and nothing is exported without approval. In M3,
  field-level accuracy is measured on a labelled set, and CI blocks regressions.
- **The validator has no authentication. Isn't that a risk?** Yes, so it is never exposed: internal ingress in
  Container Apps, ClusterIP plus NetworkPolicy in AKS, and only the worker can reach it.
- **What happens when XRechnung 4.0 arrives?** The validator image is tagged with its configuration version. We run
  3.0 and 4.0 side by side, route by the CustomizationID in the document, and store the version with every result.
- **Why Storage Queue and not a Postgres-based queue?** Native KEDA scaling to zero in Container Apps and AKS, and
  very low cost. The dual-write risk (DB insert succeeded, enqueue failed) is closed with an idempotent worker and a
  sweeper.
- **Why would anyone use this if ELSTER has a free viewer?** Viewing is commodity. The value is the workflow: one
  inbox for mixed documents, checks explained in plain German or English, and a clean handoff to the accountant.
  Whether that pain is real is exactly what the interviews test, with explicit stop criteria.
- **How did you handle sources you couldn't access?** The BMF letter PDFs couldn't be read automatically. I used the
  official BMF FAQ, which summarises them, marked the letters as a caveat, and listed reading them as an open task
  before the pilot. I never filled gaps from memory.
